# 智能体记忆检索重排序：完整实施方案

**课题：融合语义、时效与任务相关性的智能体记忆检索重排序方法研究**  
**制定日期：2026-11-13；阶段交付目标：2026-12-21。**  
依据：你提供的《现阶段工作计划》、本次对 Generative Agents 的阅读与源码核验，以及本机资源检查。

> 本文件是可执行的工作安排，不代表下述实验、其他论文阅读或数据集核验已经完成。时间为目标检查点，不是已经创建的自动执行日程。

## 1. 整个课题在做什么？

**最终目标：设计并验证一个离线、可复现的智能体记忆系统，覆盖记忆的完整生命周期——写入、维护、召回、重排与评测——并用分层实验证明各层设计对“选对证据”的贡献。**

系统输入：多轮对话、查询时点 `t_q`、当前任务状态 `z`、查询 `q`。系统输出：top-K 记忆证据，可选下游回答。评测对象：证据级排名、过时误用、历史可查性、耗时与模型调用次数。

要解决的两类失败：

1. 语义相关但已失效，例如旧地址、已取消的计划；
2. 语义不明显但影响当前决策，例如膝伤对酒店电梯需求的影响。

三个必须先说清的边界：

- **系统完整，实验分层。** 存储、更新、检索、重排都要设计，但比较时一次只改变目标层；否则无法归因。
- **重排是最后一步评分，不是全部。** 上游的表示、更新策略和候选构造决定重排上限；上游删掉历史，重排无法恢复。
- **“上下文记忆管理”在本课题中指记忆条目的生命周期管理**（写入、更新、失效、检索），不包括 MemGPT 式的 LLM 上下文窗口分页换入换出，也不是实时聊天产品。

### 1.1 两种时间与两种比较

- **访问近因性**回答“多久没被用到”；**事实有效性**回答“在 `t_q` 是否成立”。两者必须分开建模；`valid_from/valid_to` 是查询时点相关的硬约束，不是普通加分项。
- **固定候选池**用于比较重排器；**系统原生**（如 Mem0）用于端到端比较，差异可能来自抽取、维护或预算，不能混用。

### 1.2 参考架构与本项目落点

```text
多轮对话 / 文档
   → L1 写入（切分、抽取、来源、时间字段）
   → L2 维护（valid_from/to、supersedes、冲突策略）
   → L3 召回（BGE-M3 top-N；同一候选池；q 或 q+z）
   → L4 重排（有效性约束 + 语义/近因/重要性/任务相关性）
   → top-K 证据 → L5 指标 / 可选下游回答
```

| 层 | 设计内容 | 本阶段最小实现 | 实验角色 |
|---|---|---|---|
| L0 数据与任务 | 多轮对话、查询、任务状态、证据标签 | 10 段自建多轮任务；公开集小样本 | 固定 |
| L1 写入 | 事实抽取、重要性、任务标签、来源、事件时间 | 先人工/规则，后小规模 LLM 抽取 | 两种条件对照 |
| L2 维护 | 有效期、取代关系、冲突策略 | `valid_from/to` + `supersedes`；只增/覆盖/标失效 | 系统级对照 |
| L3 召回 | 统一嵌入、top-N、查询构造 | BGE-M3 dense；`q` 与 `q+z` | 固定池比较 |
| L4 重排 | 硬过滤 + 多信号融合 | 语义 / +时效 / +任务标签三方案 | 核心变量 |
| L5 评测 | Recall/MRR/NDCG、过时率、成本 | 逐题结果 + 汇总 + 失败分类 | 固定 |

### 1.3 严谨性核心：两层实验

| 实验 | 元数据来源 | 候选池 | 回答什么问题 | 不能宣称什么 |
|---|---|---|---|---|
| I 理想元数据 | 人工给对 `valid_from/to`、`supersedes`、`task_tags` | 固定 | 排序方法本身是否有效 | 不能代表自动系统的真实效果 |
| II 自动管线 | 从对话自动抽取/更新 | 系统原生 | 整套系统在真实误差下是否仍有效 | 不能把差异单独归因于排序公式 |

两层结果分开报告。实验 I 是机制验证，实验 II 是系统验证；任何一层失败都要保留并分析，不能只报成功例子。

**主排序实验的固定条件：** 维护策略固定为“标失效”（旧事实保留但补 `valid_to`），使同一候选池既能评当前查询也能评历史查询；只增/覆盖/删除只在系统级对照中改变。若预实验发现该策略不可行，再改并记录原因。

**候选池与过滤口径：** 统一候选池指召回阶段的 top-N；`valid_from/to` 过滤发生在重排阶段，属于方案的一部分。因过滤移除的条目单独记录，不与“召回失败”混算。离线评测每题恢复固定访问状态，避免前一次排序更新 `last_accessed_at` 后污染下一次近因分。

### 1.4 本阶段目标与可行性边界

**目标（至 2026-12-21）：** 完成最小系统与 10 段多轮玩具任务，每段配 2–4 个查询（现在/过去/未来），合计约 20–30 个查询级评测；跑通仅语义 / 语义+时效 / 语义+时效+任务标签三方案；输出 Recall@K、MRR、NDCG@K、耗时与模型调用次数；完成一个公开数据集的可行性检查；形成初步分层实验与消融。

**可行性约束：** 单人、六周、本机约 15.7 GB 内存与 RTX 3050 4 GB；不训练大模型，不租云 GPU；先用人工/规则元数据验证机制，再小规模测试自动抽取；付费调用需先报数量与预算。

**口径提醒：** 三方案是 P0 最小 demo，不等同于 B0–B4 全套基线；10 段任务只作流程验证和失败模式发现，不能当作 10 个独立统计样本宣称显著优势。

**明确不做：** 完整产品、实时上下文分页、完整复现 Mem0 / Generative Agents、以 10 题宣称统计显著优势。

**阶段判断标准：** 若自动抽取成本过高或质量不足，保留理想元数据实验作为主结果，并如实报告自动管线的失败；若公开数据缺少条目级证据，改用会话级评价或自建集，不伪造条目级 Recall。

## 6. 第二条工作线：平台调研怎么做才不跑偏？

按原规划保留五个问题：记忆存在哪里、何时写、怎么找、怎样处理旧信息和冲突、如何分作用域。

- **Mem0：**优先检查数据结构、提取／更新逻辑，跑一个含地址变更的小例子。明确论文机制、当前代码和实际输出是否一致。当前 2.2.1 已实测为默认 ADD-only，经典四操作提示在源码中存在但未被调用；若要对照，需另建旧版环境或手动 API。
- **一个开源 harness：**根据官方仓库是否可访问、代码是否可运行选择；重点定位上下文加载与记忆检索入口，不要求完整开发产品功能。
- **Claude Code / API、Codex、DeepSeek Harness、WorkBuddy、Letta、Zep、LangMem：**核实当前官方来源，填写五维表。产品没有公开实现时只描述已验证的产品行为，不推测底层算法。

平台结果的用途是回答“将来这个排序器能放在哪一层”。完整产品的答案质量不能直接拿来作为单独重排算法的公平对照，因为存储、抽取、模型和预算可能都不同。

## 7. 第三条工作线：选出真正能用的测评集

### 7.1 采用两类数据

**公开数据集：**检查方法在已有研究场景中的表现。优先考察 LongMemEval，LoCoMo 作为补充候选。这是筛选顺序，不代表已核验并确定最终采用。

**自建诊断集：**检查本课题特有的情况，例如未来生效、旧事实回顾、任务约束。公开集没有明确任务状态时，不强行声称它能直接检验任务相关性。

### 7.2 每个候选数据集必须过的检查

| 检查 | 要拿到的具体证据 |
|---|---|
| 正确来源 | 官方论文、仓库、下载入口及版本 |
| 授权 | 数据、代码分别允许哪些使用；是否可再分发 |
| 实际字段 | 对话、日期、问题、答案、证据、类别等，逐项核实 |
| 标注粒度 | 正确证据是会话级、轮次级还是记忆条目级 |
| 任务匹配 | 能测语义、事实更新、历史查询还是任务状态 |
| 评估脚本 | 官方指标、答案判定方式、是否依赖付费模型 |
| 划分 | 官方是否有 train/dev/test；没有时如何避免泄漏 |
| 成本 | 先跑少量样本，测时间、内存和调用费用 |

若只有答案、没有可靠的记忆证据标注，就不能直接声称计算了官方的“记忆条目 Recall”。可保留官方问答评估，另对明确标注的子集做检索诊断。

若证据标注只到会话级，就先报告会话级检索结果；转到更细粒度必须给出额外标注和验证过程。抽取出来的新“事实记忆”也不能自动继承原始对话的证据 ID。

### 7.3 选择决策与退路

- 有可用时间／更新问题，且协议可复现：作为主要公开候选。
- 能做问答，但不支持精确检索标注：用于下游回答评价，自建集用于排序评价。
- 需要付费 judge：先做无需付费的样本检查和检索部分；正式答案评价再确定预算，替代 judge 时明确说明协议变化。
- 数据不可获取或授权不清：记录失败原因，选择其他公开来源，不擅自再发布。

**交付：**一张选择表、一份数据使用说明、若干人工核对样例、适配代码，以及明确的“主用／补充／不采用”结论。

## 8. 第四条工作线：基线复现

### 8.1 什么叫基线？

就是与自己的方法完成相同题目的现有办法。不能把别人论文里的成绩直接复制过来与自己不同数据上的成绩比较；应在统一条件下重新运行。

### 8.2 实现顺序和具体范围

| 编号 | 方法 | 地位 | 实现内容 |
|---|---|---|---|
| B0 | 仅语义 | 必做 | 统一 embedding，按 cosine 排序 |
| B1 | 语义 + 访问近因性 | 必做 | 检查单独增加时间项的效果 |
| B2 | GA-paper | 必做 | 按论文计算近因性、重要性、相关性，归一化后等权相加 |
| B3 | 强语义重排器 | 目标完成 | 对统一候选池用现成 Cross-Encoder 重排 |
| B4 | GA-paper 调参版 | 正式比较前补齐 | 在开发集调权重与衰减，避免只比较未经调优的基线 |
| P0 | 原规划三项 demo | 必做 | 语义 + 明确说明的时间项 + 简单任务标签分数 |
| P1 | 研究候选方法 | 逐步完成 | 改进时间有效性与任务状态评分，分别消融 |

GA-code 的源码差异保留为附加核验，不优先复现整套 Smallville。Mem0、Zep 首先作为机制与系统参考；只有能统一输入、模型和预算时，才考虑完整系统对照。

### 8.3 统一条件

- 所有主要方法使用同一记忆切分和同一 embedding 模型。
- 重要性分数一次生成并缓存，各方法共享，注明来源。
- 固定向量／人工重要性只用于公式验证；不能把它当作原论文的模型评分结果。
- 先在小规模全量记忆上打分；随后使用统一候选池比较重排。
- 查询 q 与任务状态 z 的构造一致；增加 `q+z` 的强语义对照，检验提升是否只是多给了信息。
- 正确记忆没进入候选池时，单独记录为召回问题；不全算成重排问题。
- 离线每题恢复固定状态，避免访问时间更新污染后续比较。
- 模型版本、K、候选数 N、上下文预算和并列规则全部记录。

### 8.4 模型与本机资源

本次读取到本机约 **15.7 GB 内存、NVIDIA RTX 3050 4GB Laptop GPU**。这不等于已完成性能压测。

优先采用现成 embedding 与重排模型，不安排大模型训练。bge-m3 是原计划候选，先用小样本测峰值内存、耗时和输入长度；若 GPU 容量不足，采用 CPU／小批量推理或更轻模型，并让所有主要方法使用同一配置。调整模型时更新实验版本，不混合比较。

所有 embedding、importance 和模型重排结果尽量缓存。完整模型下载前先检查磁盘与下载规模；需要付费服务时另列预计调用量和预算，不以“完整权限”代替费用约定。

## 9. 第五条工作线：自建测试题与记忆格式

### 9.1 先做 10 个任务验证流程

覆盖：地址更新、计划改期、长期过敏、历史查询、未来生效、临时例外、任务必要信息、语义相似干扰、高重要性干扰、无充分证据。

每个任务至少包含历史记忆、任务状态、问题、查询时点、正确证据与判定理由。数量是起步范围，不是统计充分性的保证。

### 9.2 再扩展为 20–50 个独立任务

每个任务可有 2–4 个不同查询，例如“现在是什么”“过去是什么”“某日期会是什么”。**同一任务的查询都放在同一个数据划分中**，防止一边看答案调参、一边用它的改写做测试。

扩大数据前先冻结标注规则，挑选一部分进行人工复核。任务量、问题量、类别量分别记录，不能把一段对话拆成许多问题就宣称有同样多的独立任务。

用户优先复核所有有歧义的例子，以及每类一小部分样本；正式论文若条件允许，再邀请第二位人工复核者。两次模型判断一致不等于两名独立人工标注一致。

### 9.3 最小记忆字段

```text
id                  唯一编号
content             内容
created_at          何时存入系统
last_accessed_at    何时被访问
valid_from/to       事实在何时适用；无法确定时允许为空
source              原始消息来源
kind                用户事实、计划、模型推断等
supersedes          新记录替代哪些旧记录
task_tags           任务标签，明确人工标注还是自动提取
importance          重要性分数及其来源
embedding_key       向量缓存标识
```

不要求第一天把所有字段都自动抽取出来。先用人工明确字段验证排序机制，再测试自动抽取带来的误差。

**必须区分两种实验：**

- 给定正确标签／有效期时，排序器能否有效利用它们？
- 从真实对话自动抽取这些字段时，整套方法是否仍有效？

第一种是理想元数据实验，应明确标记；不能只给自己的方法人工正确标签，却不说明信息优势。

## 10. 方法设计：先验证简单方案，不先承诺复杂模型

把课题拆成三个可验证问题：

- **RQ1：**在相同语义候选池中，多因素排序能否改善正确证据的排名？
- **RQ2：**区分访问近因性与事实有效性，能否减少旧信息误用，同时保留历史查询能力？
- **RQ3：**明确加入任务状态，能否找回语义不明显但会影响当前决定的记忆？

第一版先实现任务标签匹配或简单规则，检查是否存在增益。之后再考虑让现成重排器或 LLM 同时读取“问题 + 任务状态 + 记忆”，判断是否会改变当前决策。

注意“同类任务标签匹配”只是任务相关性的粗略近似，不是自动成立的创新点。正式比较应包含只用 query、使用 query+task_state 的语义基线，区分输入信息增益和算法增益。

权重先保留一个可解释的固定版；需要调参时，只在开发集进行，冻结后再看测试结果。小规模数据优先考虑简单模型与少量参数，避免复杂训练压过研究问题。

## 11. 实验设计：到底比较什么？

### 实验 A：公式与程序是否正确

用手工可算的小样例验证：近因性方向、归一化、加权、并列、空候选、时间格式、访问状态隔离。输出原始分项、归一化分项、总分和排名。

### 实验 B：主要排序比较

在固定数据上运行 B0、B1、B2，随后加入 B3 与自己的方法。初期 K 取 1、3、5；数据规模允许时再增加。正式记录每题结果，而不只报告总体平均。

### 实验 C：时间与冲突专项

分别统计当前事实、历史事实、未来生效、临时覆盖、长期稳定事实。检验是否出现“改善当前查询，但损害历史查询”的代价。

### 实验 D：任务相关性专项

构造“语义相近但无用”和“语义不明显但必要”的成对样例。确保任务背景足以支持判定，不把可能未来有用的信息都当作当前必要证据。

### 实验 E：消融与参数

去掉时间有效性、去掉任务状态、替换成简单规则；比较各项贡献。对少数关键权重和时间尺度做开发集敏感性分析，给已有基线同等调参机会。

### 实验 F：下游回答与成本

排序实验可靠后，再将选出的记忆交给同一个回答模型，检查答案质量、过时事实误用及拒答。固定提示与预算。记录排序耗时和端到端耗时，分开报告缓存与非缓存结果。

### 指标与解释

| 指标 | 在问什么？ |
|---|---|
| Recall@K | 正确证据有多少进入前 K 条？ |
| MRR | 第一条正确证据排得有多靠前？ |
| NDCG@K | 按分级价值看，整体排序是否合理？ |
| 过时返回率 | 返回内容中有多少对这次查询已经失效？ |
| 完整证据命中率 | 多条必要证据是否一起找齐？ |
| 候选 Recall@N | 重排前是否已经漏掉正确证据？ |
| 回答质量 | 选出的记忆是否帮助模型答对？ |
| 时间与成本 | 增益需要付出多大代价？ |

缺少细粒度证据标注时，不强行计算相应检索指标。无答案题单独评估拒答／证据不足判断。按任务汇总并估计不确定性，不把同任务的相关问题当作完全独立数据。

若效果不提升，先区分：召回没找到、重排排错、元数据错、任务定义不清、下游模型用错。负结果要保留，不删掉不利样本来制造提升。

## 14. 关键决策与停止条件

| 情况 | 怎么处理？ |
|---|---|
| 公开数据没有条目级证据 | 保留其官方问答评价；检索评价用有标注子集或自建集 |
| 本机模型运行很慢／显存不足 | 先小样本、CPU、缓存或轻模型；不未经验证承诺规模 |
| Mem0 或某平台示例依赖不可用 | 定位原因并记录，不让它阻塞独立排序模块 |
| GA 论文与代码不一致 | 主线按论文定义；代码差异单独记录，不暗中混合 |
| 原型只在人工标签下有效 | 明确理想元数据条件；自动标签实验单独报告 |
| 新方法不优于强语义重排 | 分析任务定义与增益来源，调整或收缩主张 |
| 数据量小、波动大 | 报告探索性结果，不宣称普遍显著优势 |
| 时间不足 | 优先可靠的基线、数据和协议；削减平台深挖与界面美化 |
