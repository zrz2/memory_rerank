# Mem0：核心笔记

来源：arXiv:2504.19413v1（2025-04-28），本地 PDF `data/raw/mem0/mem0_2504.19413.pdf`；复现对象 `mem0ai==2.2.1`；查阅 2026-11-15。核心部分为论文原文，源码与实测证据见附录。

## 1. 它解决什么问题？

跨会话的长期记忆。聊天记录越来越长，不能全放进上下文，直接截断又会忘掉关键事实。Mem0 要解决三件事：**从对话里记什么、新旧事实怎么处理、需要时怎么取**。

对本课题最关键的一点：Mem0 **不输出候选排名**，它决定的是“记忆库里还剩哪些条目”。所以它不是排序器，而是**候选池的维护者**——上游删了什么、留了什么，直接决定下游重排器还有没有证据可排。

## 2. 核心办法是什么？

每条新消息对 `(m_{t-1}, m_t)` 走两阶段：

```
提取：摘要 S + 最近 m=10 条 + 当前消息对 → 候选事实 Ω
更新：对每个 ω，检索 top s=10 条相似旧记忆
      → LLM 用工具调用选一个操作：
         ADD / UPDATE / DELETE / NOOP
```

不是训练分类器，而是让 LLM 在函数调用里选。图版本 **Mem0^g** 把记忆存成标签图，冲突时**把旧关系标记 invalid，而不是物理删除**；检索走“实体为中心 + 语义三元组”两路。

### 2.1 三种维护策略（本课题的核心对照）

| 策略 | 行为 | 旧事实 | 当前查询 | 历史查询 |
|---|---|---|---|---|
| 只增 | 2.2.1 默认 ADD-only | 原地保留 | 新旧并存，可能排错 | 可答 |
| 删旧 | 论文稠密版 DELETE | **物理消失** | 干净 | **答不出** |
| 标失效 | Mem0^g 旧边 invalid | 保留但失效 | 干净 | 可答（需时间推理） |

论文只测了答案质量，**没有测这三种策略对检索排序的影响**。这正是本课题可以补的空白。

### 2.2 具体例子（本地实测 2.2.1，非论文）

最小示例依次说“2025 年 3 月搬到北京 → 花生过敏 → 实际上搬到上海并住在那里”。3 轮全部 **ADD**，北京条目没有被覆盖或删除。

问“现在住哪”：

| 排名 | 记忆 | 分数 |
|---:|---|---:|
| 1 | 搬到北京（旧） | 0.6484 |
| 2 | 搬到上海（当前） | 0.6304 |
| 3 | 花生过敏 | 0.5712 |

正确当前地址在上海，但旧北京排第 1；按上海为 gold 计算 rank = 2、MRR = 0.5。

诊断集 `address_current` 同样复现：旧杭州 0.6122 排第 1，新上海 0.5710 排第 2，MRR = 0.5。只增策略下**过时事实排前**。

论文描述的 DELETE/UPDATE 与 Mem0^g 的 invalid 标记提供另一种极端——删旧后历史查询无证据。2.2.1 默认不执行这些操作；改用官方仓库论文同期 tag 后，已实测到 UPDATE 覆盖与 DELETE 删旧（见 §2.3）。两种极端都说明：维护策略与排序器是耦合的。

### 2.3 论文同期代码的四操作实测

论文正文写明 `Code can be found at: https://mem0.ai/research`，该页面指向官方仓库 `https://github.com/mem0ai/mem0`。本课题用官方 tag `v0.1.94`（commit `07ddd7cb`，2025-04-26；arXiv v1 发布前最后一个 tag）实际运行，而不是只看 2.2.1。

5 轮受控对话的实际决策：

| 轮次 | 输入 | 决策 |
|---:|---|---|
| 1 | 搬到北京、在字节工作 | ADD 北京；ADD 字节 |
| 2 | 花生过敏 | ADD 过敏；旧记忆 NONE |
| 3 | 实际搬到上海 | **UPDATE** 北京→上海；ADD 当前住上海 |
| 4 | 更正：从未入职字节 | **DELETE** 字节；ADD 从未入职 |
| 5 | 仍然花生过敏 | 全部 **NONE** |

四操作都真实出现；`NONE` 不出现在 `add()` 返回值里，只能从原始 LLM 响应看到。两个后果与本课题直接相关：

- **UPDATE 覆盖旧值**：北京被改写成上海，“以前住哪”也搜不到北京，历史事实丢失；
- **DELETE 物理删除**：字节条目消失，“在哪工作”没有对应证据。

源码核对：`main.py:244` 检索 `limit=5`（论文 §2.1 写 `s=10`，存在版本差异）；`:261` 调四操作提示；`:302/:317/:326` 分别处理 UPDATE/DELETE/NONE。详细结果与调用账本见 `experiments/mem0/paper_mechanism/README.md`。

### 2.4 检索怎么打分

- 论文：稠密相似度取 top，交给 LLM 答题；没有重排器。
- 2.2.1 源码：组合分 = 语义 + BM25 + 实体增益，**没有 recency 项、没有有效期项、没有任务相关性项**（`utils/scoring.py:57,101,118`）。
- 2.2.1 `search`：`top_k=5`，内部先取 `max(top_k×4, 60)` 条候选再融合；没有 `target_time` 参数。

## 3. 哪些参数固定、哪些学习得到、哪些未说明？

| 类别 | 内容 |
|---|---|
| 固定 | `m=10`；`s=10`；四种操作语义；抽取与更新由 LLM 决策；实验用 GPT-4o-mini |
| 学习得到 | **无**。无排序权重训练，四操作靠提示词约束 |
| 未说明 | 提取/更新的完整提示词（附录只给裁判与答题提示词）；摘要长度与刷新频率；事实去重阈值；图版本相似度阈值 τ；操作选择错误的处理 |

## 4. 用什么题目和指标验证？

LOCOMO：10 段长对话，每段约 600 轮、平均 2.6 万 token，约 200 题；单跳、多跳、时序、开放域四类，对抗类因无标准答案被排除。

指标：F1、BLEU-1、LLM-as-a-Judge（J），跑 10 次报均值 ± 标准差；另测 token 与延迟 p50/p95。

| 方案 | 总体 J | token | 总延迟 p95 |
|---|---|---|---|
| 全部上下文 | **72.90** | 26031 | 17.1 秒 |
| Mem0 | 66.88 | **1764** | **1.44 秒** |
| Mem0^g | 68.44 | 3616 | 2.59 秒 |

结论是**便宜、快、够用**，不是最准。

**能说明**：抽取 + 维护的管线在答案级任务上接近全上下文，同时大幅省 token。
**不能说明**：没有 Recall/MRR/NDCG，答错时分不清是“没检索到”还是“生成错”；没有对四种操作做消融，无法判断维护策略本身贡献多少。

## 5. 没解决什么，与本课题是否相关？

- **维护策略未评测**：删旧、只增、标失效只比答案分，没比检索排名，也没区分当前查询与历史查询。
- **没有有效期字段**：稠密版无 `valid_from/valid_to`；Mem0^g 的 invalid 标记只存在图里，不能直接用于扁平候选池。
- **没有任务相关性**：抽取时不知道未来任务，候选池可能缺证据，也可能留噪声。
- **会丢历史**：DELETE 物理删除，UPDATE 覆盖旧值，“我以前住哪”类问题无证据可排。
- **候选池不可控**：维护结果决定池子大小与构成，重排器只能在既有池内工作，无法恢复被删条目。

**与本课题的关系**：它不是排序基线，但提供了 RQ2 最直接的系统级对照——**同一份对话，用三种维护策略跑，再看当前/历史两类查询的候选池差异**。这能回答“重排的上限是否已被上游维护策略决定”。

## 6. 复现、借鉴、比较，还是仅作背景？

**比较。** 输出答案而非候选排名，不能作排序基线；作为“维护与冲突处理”的系统级对照。本地已复现 2.2.1：默认只增、过时事实可排前；另用官方仓库论文同期 tag `v0.1.94` 实测四操作（UPDATE 覆盖、DELETE 删旧、NONE 不变）。数据与结果收在 `experiments/mem0/`，不追论文表 1 数字。逐次复现细节见 `experiments/mem0/REPRODUCTION.md`。

**决策：这篇论文对本课题的用途是——作为“维护与冲突处理”的系统级对照基线，用来比较“删旧 / 只增 / 标记失效”三种策略如何改变当前查询与历史查询的候选池，从而界定重排器的可作用边界，而不是作为排序基线。**
